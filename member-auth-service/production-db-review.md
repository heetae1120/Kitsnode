# 회원 인증 운영 DB 변경 검토안

상태: **2026-11-10 운영 스키마·역할 적용 완료**. 대상은 Supabase `kits`의 `postgres` 데이터베이스다. 사용자가 자동 백업이 없다는 사실을 확인하고 백업 없이 적용을 승인했다. 비밀번호 설정, Worker·스케줄러 배포, 네이버 콜백 등록, 로그인 시험 또는 프론트 발행은 승인과 적용 범위에 포함되지 않았다.

## 적용 범위

후보 SQL은 단일 트랜잭션에서 비공개 스키마 `member_auth`, `member_auth_support`를 만들고 각각 인증용 4개, 약관·동의·OAuth state·요청 제한용 4개 테이블을 생성한다. 각 테이블은 RLS를 켜고 PUBLIC 권한을 제거한다. `member_auth_runtime`은 로그인 불가능한 권한 그룹, `member_auth_service`는 그 그룹의 권한을 상속하는 서버 전용 로그인 역할, `member_auth_maintenance`는 별도의 정리 전용 로그인 역할이다. 두 로그인 역할은 암호가 없어 최초 생성 직후 암호 인증으로 접속할 수 없다. 서비스 역할의 기본 search_path는 `member_auth, pg_catalog`이다. 암호와 운영 약관, 사용자·세션은 SQL에 포함하지 않는다.

기존 테이블과 기존 역할을 수정하거나 기존 공개 API 설정을 변경하지 않는다. 이름 충돌이 있으면 실패하도록 `IF NOT EXISTS`를 사용하지 않는다. 5초 lock timeout과 문장당 60초 timeout을 둔다. SQL은 모두 완료되거나 트랜잭션 전체가 롤백되어야 한다. 적용 수단이 트랜잭션이나 역할 생성, 세션 설정을 지원하는지 미리 확인하고 후보 파일을 불필요하게 조각내지 않는다. 실제 적용 전 마이그레이션 관리 도구의 버전·기록 방식을 결정하고 이력과 적용 대상의 일치를 확인한다.

## 권한 검토

- 인증 4개 테이블에는 서버의 SELECT/INSERT/UPDATE/DELETE와 해당 역할에 한정한 RLS 정책이 있다. support의 약관은 SELECT/INSERT/UPDATE, 동의와 state는 SELECT/INSERT, 요청 제한은 SELECT/INSERT/UPDATE다. 클라이언트 역할에는 권한을 부여하지 않는다.
- RLS는 소유자와 BYPASSRLS 역할에 대한 경계가 아니다. 서비스 계정이 소유자·superuser·BYPASSRLS가 아닌지, 멤버십에 의한 권한 상승이 없는지 실제로 확인한다. 암호는 안전한 별도 경로로 전달하고 로그·채팅·파일·명령 기록에 남기지 않는다.
- 2026-11-10 운영 DB의 읽기 전용 점검에서 대상 두 스키마와 두 역할은 없었다. `public` 스키마는 PUBLIC에 USAGE를 허용한다. PUBLIC SELECT 권한을 가진 객체 2개가 발견됐지만 해당 시점에 PUBLIC 스키마 USAGE까지 동시에 허용된 읽기 가능한 관계 객체는 없었다. PUBLIC 함수 EXECUTE, 다른 상속 권한, 향후 권한 변경까지 이 관찰로 배제할 수 없다. 전용 계정이 기존 객체에 접근하지 못한다고 아직 보장하지 않는다. 운영 DB 생성 후 그 계정으로 실제 관계·함수·스키마 권한을 점검하고 예상 밖의 접근이 있으면 서비스 연결을 중단한다. 기존 PUBLIC 권한의 일괄 REVOKE는 다른 서비스를 깨뜨릴 수 있으므로 이 변경에 포함하지 않는다.
- 운영 DB의 기존 default ACL에는 `public` 등 기존 스키마에서 `anon`, `authenticated`, `service_role`에 부여되는 항목이 있다. 이번 스키마는 아직 없어 해당 스키마 전용 항목은 없었으나, 적용 주체의 전역 default ACL과 실제 생성 후 ACL을 재확인하고 anon/authenticated의 스키마 USAGE와 테이블 접근이 없는지 검증한다. PUBLIC REVOKE만으로 다른 역할에 대한 명시적 부여가 제거되는 것은 아니다.
- `member_auth_maintenance`에 support 스키마 USAGE, state 테이블의 `expires_at` 열 SELECT 및 DELETE만 부여한다. RLS는 SELECT와 DELETE 모두 `expires_at < now()`인 행으로 제한한다. 이 역할은 digest 조회나 다른 회원 테이블 접근 권한, runtime 그룹 멤버십이 없다. 인증 서버 역할에는 DELETE를 부여하지 않는다. 이것은 기존 객체에 대한 PUBLIC 상속 권한까지 제거한다는 의미는 아니다.
- `request_limits`는 전체 요청에 대한 단일 전역 제한이다. 개별 IP/계정별 제한을 제공하지 않는다. 신뢰 가능한 Cloudflare 경계와 계정별 제한 검증은 별도 출시 조건이다.

## 적용 전 확인

1. 운영 DB의 최신 백업/복구 가능 시점과 복원 절차, 마이그레이션 담당자 및 적용 창을 확인한다. 대상 DB와 스키마·역할 이름 부재, 현재 마이그레이션 이력, 잠금 상태를 다시 확인한다. 로컬 테스트는 운영 백업 검증이 아니다.
2. 현재 후보 SQL과 배포 버전의 Better Auth 스키마를 다시 비교하고, 역할 생성 권한 및 DB 연결 방식·Hyperdrive TLS 검증과 pooling/search_path 호환성을 확인한다. 원본 DB 연결에 관리자 역할을 사용하지 않는다.
3. 실제 약관과 개인정보 안내가 확정되지 않았으므로 핸들러를 시작하지 않는다. 현재 핸들러 초기화는 약관 버전·해시를 DB에 기록한다. 합성 약관과 시험 계정을 운영 DB에 넣지 않는다.
4. 스키마 적용 뒤 실제 로그인 계정을 별도로 안전하게 설정하기 전까지 Worker는 비활성 상태로 둔다. 전용 역할의 타 스키마 접근·RLS·원자적 state 소비 및 동시 연결을 검증하고, 실제 Hyperdrive에서 별도로 확인한다.

## OAuth state 정리 운영안

- 실행 시각은 **매일 03:00 KST (전날 18:00 UTC, cron `0 18 * * *`)**다. 애플리케이션은 claim 시 만료 시각을 생성 시점 24시간 뒤로 기록하므로 `DELETE FROM member_auth_support.oauth_state_claims WHERE expires_at < now()`는 그 시점 이후에만 행을 삭제한다. 실제 삭제는 실행 시각에 따라 만료 후 최대 약 하루 지연될 수 있다.
- 실행자는 인증 Worker와 분리된 정리 전용 스케줄러다. `member_auth_maintenance`의 별도 자격 증명과 검증된 TLS 연결을 사용하고, 각 실행에는 제한 시간과 실패 알림을 설정한다. 2회 연속 실패 또는 미처리 행의 증가가 발견되면 조사한다. 정리는 멱등적이며 실패 시 다음 실행에서 재시도한다. 대량 누적으로 시간 제한에 걸리면 배치 처리 계획을 검토한다.
- `state-cleanup-worker.mjs`와 `wrangler.state-cleanup.example.jsonc`는 로컬 구현 후보이며, 일일 UTC 18:00(한국 03:00) 실행과 별도 `MAINTENANCE_HYPERDRIVE`를 사용한다. 기본 설정은 비활성이고 HTTP 요청은 404다. 실제 정리 역할이 아닌 연결은 삭제 전에 거부한다. 로컬 제한 역할 테스트에서 만료 행만 삭제하고 미만료 행이 남았다. 운영 DB에 정리 작업은 실행하지 않았다.
- **스케줄러는 아직 배포·등록되지 않았다.** 정리 역할 비밀번호와 별도 Hyperdrive는 미설정이며 서비스 역할의 Hyperdrive를 재사용하면 안 된다. 운영 활성화 전 자격 증명·인증서 검증·캐시 비활성, 실제 역할, Cron 동작 및 실패 알림 구성을 확인한다. 현재 구현은 만료 행을 한 번에 삭제하며 큰 누적 시 실행 시간과 잠금 영향을 측정하고 배치 방안을 검토해야 한다. 실패 알림과 2회 실패 감시는 아직 구현·설정되지 않았다. 운영 변경 승인에 스케줄러 배포는 포함되지 않는다.

## 실패 및 롤백

- SQL 실행 중 오류라면 트랜잭션 전체 롤백 여부를 확인하고 스키마·역할·마이그레이션 이력의 잔존 여부를 읽기 전용으로 조사한다. 실패 원인을 수정하기 전 무조건 재시도하지 않는다.
- 적용 성공 후 서비스 연결 전이라면 우선 비밀번호가 없는 계정을 유지하고 Worker를 중지한다. 데이터가 없는 것을 확인한 뒤 소유권·의존성과 마이그레이션 이력을 검토해 역순 제거할 수 있다. 롤백 SQL의 실제 실행은 별도 승인과 검증 후 진행한다.
- 회원·세션·동의 기록이 생긴 이후에는 **스키마 DROP이나 백업의 전체 DB 복원을 자동 실행하지 않는다**. 먼저 Worker를 차단하고 해당 로그인 역할의 접속을 중지하며 연결 풀을 종료한다. 기존 세션 연결은 별도 종료가 필요할 수 있다. 데이터 보존·영향과 복구 시점을 확인하고, 필요한 경우 범위를 한정한 복구 계획을 수립한다. 전체 DB 복원은 다른 서비스 데이터에도 영향을 줄 수 있다.
- 운영 전 비상 중지 후보는 `ALTER ROLE member_auth_service NOLOGIN` 및 필요 시 `ALTER ROLE member_auth_maintenance NOLOGIN`이다. 이는 신규 로그인만 막고 기존 연결이나 이미 발급된 브라우저 세션을 자동으로 종료하지 않는다. 세션·연결 폐기와 복구 절차를 별도 실행한다. 비상 조치 역시 실행 권한과 승인 절차를 확인한다.

## 검증 결과와 한계

- 2026-11-10 Cloudflare Hyperdrive `kitsnode-member-auth`를 전용 서비스 역할로 구성했다. Supabase CA `verify-full`, 쿼리 캐시 비활성, 원본 연결 제한 5를 설정했다. 임시 Workers 원격 미리보기에서 실제 운영 DB에 전용 계정으로 연결하고 읽기 쿼리를 실행했으며 `member_auth, pg_catalog` 검색 경로와 인증 스키마 USAGE, 회원 테이블 SELECT, state DELETE 거부를 확인했다. 회원 데이터나 약관은 조회·생성하지 않았다. 시험 미리보기를 종료했다. 실제 네이버 로그인, 동시 연결 및 스케줄러는 검증하지 않았다.
- 운영 마이그레이션 `20261109165239_kitsnode_member_auth_schema_roles` 적용 성공 및 이력 등록 확인. 후보 SQL SHA-256 `cf84824b22184fe08f450b11e790425a0a836a846df165f088fed459052d8666`. 8개 테이블에서 RLS가 활성화됐고 소유자는 postgres다. 두 로그인 역할은 비밀번호가 없고 superuser·CREATEROLE·CREATEDB·BYPASSRLS가 아니다. 서비스 역할만 runtime 그룹 권한을 상속한다.
- 운영 카탈로그의 유효 권한 검사에서 anon/authenticated의 새 스키마·테이블 접근, 서비스 및 정리 역할의 다른 사용자 스키마 내 관계·시퀀스·함수 접근이 발견되지 않았다. 정리 역할은 state 만료일 SELECT와 DELETE, 서비스 역할은 state DELETE가 없으며 정리 역할은 digest SELECT가 없다. 정리 RLS 정책은 만료된 행으로 제한한다. PUBLIC의 DB CONNECT/TEMP 상속은 남는다. 실제 로그인·Hyperdrive에서의 쿼리와 RLS 동작은 비밀번호 설정 전이므로 아직 검증하지 못했다.
- 보안 advisor는 기존 `kits_ai_private`와 `public`의 RLS 정책 없는 테이블 6개를 INFO로, Supabase Auth 유출 비밀번호 보호 비활성화를 WARN으로 보고했다. 새 회원 인증 테이블에 대한 해당 항목은 없었다. 정책 없는 RLS는 의도적 차단일 수 있으므로 기존 서비스를 검토하지 않고 변경하지 않았다.
- 로컬 전용 일회성 PostgreSQL DB에 후보 SQL을 적용했다. 8개 테이블의 RLS 활성화, 별도 LOGIN 계정 연결, search_path, 약관 INSERT 및 관련 권한을 확인했다. 수정된 후보로 정리 계정이 만료 행 1개만 삭제하고 미만료 행 1개를 보존하며 digest와 약관을 읽지 못하고, runtime은 state DELETE를 하지 못하는지 검증했다. 정리 역할이 runtime 멤버가 아닌 것도 확인했고 시험 DB와 역할은 삭제했다.
- 첫 로컬 시도는 로컬 관리자에 테스트 로그인 역할의 SET ROLE 권한이 없어 실패했다. 테스트 계정으로 직접 접속해 다시 검증했다. 이 로컬 테스트는 Supabase 관리 API의 마이그레이션 실행 권한, 실제 Cloudflare Hyperdrive 및 운영 데이터 격리의 증명이 아니다.
- 운영 적용 뒤에는 테이블·정책·권한, 기존 서비스 회귀, 전용 역할의 실제 유효 권한과 Hyperdrive 연결을 검증해야 한다. 실제 로그인은 확정된 약관, 시험 데이터 정책 및 별도 승인 이후에만 진행한다.
- 운영 DB 읽기 전용 재검사에서는 PUBLIC의 스키마 USAGE와 조합해 접근 가능한 사용자 관계 객체·시퀀스·함수가 없었다. PUBLIC의 DB CONNECT 및 TEMP는 허용되고 CREATE는 허용되지 않는다. 이는 장래의 권한 변경이나 실제 생성된 역할의 모든 유효 권한을 검증한 결과는 아니다. 생성 후 별도 계정으로 재검증 전까지 Hyperdrive 연결을 허용하지 않는다.
