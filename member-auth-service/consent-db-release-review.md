# 약관별 동의 운영 DB 변경 검토안

상태: 검토용. 운영 `kits` DB에는 적용하지 않았고 SQL 실행·활성화·공개 배포는 이 문서로 승인되지 않는다. 대상 후보는 `../supabase/migrations/20261110063351_member_document_consents.sql`이며, `review-drafts/` 대안 SQL은 적용하지 않는다. 기존 `production-db-review.md`는 기존 인증 스키마 적용 당시 기록이다.

## 변경과 권한

- `member_auth_support`에 버전별 약관 본문·해시, 현재 적용 버전, 계정별 동의를 새로 만든다. 두 문서 유형 `terms`, `privacy`의 현재 포인터는 생성 직후 비어 있어 서버는 실패 처리한다. RLS를 켜고 `PUBLIC`, `anon`, `authenticated`, `service_role` 및 runtime의 기존 접근을 명시 철회한다. runtime 그룹은 버전 및 동의 SELECT/INSERT와 포인터 SELECT만 부여한다. 기존 단일 문서 `terms`, `consents`에 대한 runtime 권한 철회로 이전 서버는 접근에 실패한다. 기존 동의를 두 문서의 동의로 복사하지 않는다.
- 약관별 텍스트는 공개용이어도 개인 식별자나 비밀값을 넣지 않는다. 버전 변경은 새 레코드와 포인터 갱신으로 수행한다. DB의 런타임 계정에는 포인터 쓰기 권한이 없으며 변경은 별도 승인된 관리자 역할로 한다. 포인터 트리거와 동의 트랜잭션은 같은 advisory lock을 사용하므로 변경 중 동의 기록이 오래된 버전을 사용하지 않도록 대기 또는 실패한다.
- 실제 적용 후 전용 로그인 계정의 상속 권한과 소유자·BYPASSRLS 여부, public 등 다른 스키마의 기본 및 상속 권한, Data API 스키마 노출, 각 테이블·함수의 ACL을 다시 확인한다. RLS와 GRANT는 서로 다른 경계이며 `service_role`의 BYPASSRLS는 권한을 자동으로 부여하지는 않는다. 기존 공개 권한을 일괄 변경하지 않는다. 기본 ACL이나 다른 역할에서 권한이 상속될 수 있으므로 운영 환경의 최종 유효 권한 검사가 필요하다.

## 사전 조건과 순서

1. 확정된 이용약관과 개인정보 안내 전문·독립 버전·SHA-256·필요 고지를 검토하고 안전한 릴리스 기록에 보관한다. 사용자에게 제공되는 문구와 서버의 본문 및 해시가 일치해야 한다. 법적 적합성은 이 기술 검토만으로 확정되지 않는다.
2. 실제 복구 가능한 백업과 범위별 복원 절차를 준비·검증하고, 마이그레이션 이력·이름 충돌·역할 상속·영향받는 기존 작업자를 읽기 전용으로 점검한다. 무료 플랜 자동 백업 여부는 현재 계정 설정을 확인한다. 스키마 후보는 `BEGIN`/`COMMIT`이므로 도구가 하나의 트랜잭션으로 처리하는지, `lock_timeout=5s`와 `statement_timeout=60s`를 지원하는지 확인한다. Supabase CLI v3는 이전과 원격 대상 지정 방식이 다르므로 실행 전 버전과 대상, 이력 기록 방식을 확인한다.
3. 회원 경로를 차단하고 인증 Worker의 중복 구버전과 활성 연결을 정리한 뒤 승인된 SQL을 적용한다. 적용 시 기존 단일 문서 서비스 권한이 즉시 끊겨 무중단 배포가 아니다. 다른 API와 state 정리 Worker는 별도로 회귀 검증한다. SQL 성공과 DB migration 이력 일치를 확인한다.
4. 권한 있는 관리자가 리뷰된 두 문서 버전·본문·해시를 등록한 뒤 현재 포인터 두 개를 한 트랜잭션에서 맞춘다. 기존 포인터를 바꾸는 관리자 트랜잭션에는 시간 제한을 두고 예상 잠금 대기와 권한이 적절한지 확인한다. 인증 Worker 번들은 정확히 같은 문서 버전·본문·해시를 포함해야 한다. 포인터를 하나만 바꾸거나 번들이 다른 인스턴스는 실패 처리된다. 설정을 끝내기 전 회원 경로를 열지 않는다.
5. 운영 전용 계정과 실제 Hyperdrive에서 TLS 검증·search_path·권한 및 런타임 쿼리를 확인하고, 격리 환경에서 동의 각각의 필수 여부·오래된 버전 거부·동시 변경·실패 복구를 실험한다. 실제 회원 데이터가 없는 승인된 별도 시험 DB와 합성 입력을 사용한다. Hyperdrive max origin connections 및 트랜잭션 풀링과 advisory lock 동작을 실제로 점검한다. 각 Worker 풀은 max 2이나 여러 Worker가 Hyperdrive의 원본 연결 한도(기존 확인 5)를 공유할 수 있고, 장시간 잠금이나 다른 DB 작업으로 지연될 수 있다. 이메일 가입은 단일 진입 보호가 있어 동시에 일부 요청이 503을 받을 수 있다. SENS는 계속 비활성이고 이메일 가입 활성화 전 이를 별도 부하 검증한다.
6. 프론트와 인증 서버의 동일 출처, 쿠키, 네이버 정식 콜백·검수, 운영 약관 제공·동의 기록과 장애 감시를 확인한 뒤 별도 승인된 공개 절차를 진행한다.

## 실패와 롤백

- SQL 오류 시 전체 트랜잭션 롤백과 migration 이력을 조회해 확인한다. 자동 재시도, 임의의 `DROP`, 사용자 동의 삭제는 하지 않는다. 기존 단일 문서 runtime 권한 REVOKE도 트랜잭션 안에서 롤백되는지 확인한다.
- SQL 성공 후 활성화 전 문제라면 공개 회원 경로를 닫고 연결·스키마와 포인터를 조사한다. 새 동의 기록이 존재한다면 기록을 보존하고 필요한 범위만 백업한다. 구버전 서버를 되살리기 위해 곧바로 기존 단일 동의 권한을 복원하지 않는다. 구버전은 분리 동의를 검증하지 않으므로 공개가 안전하지 않다.
- 문서 개정 후 되돌리기는 버전 포인터, 배포된 번들 및 동의 재확인 정책을 함께 검토해야 한다. 이전 포인터로 되돌리면 과거 동의가 다시 유효하게 보일 수 있어 자동 롤백은 금지한다. 법무·운영 검토와 데이터 보존을 전제로 승인된 새 버전의 정정/정방향 복구를 우선 검토한다. DB 백업 전체 복원은 다른 서비스 데이터를 덮을 위험이 있어 자동 실행하지 않는다.

## 로컬 검증과 한계

격리 PGlite에 현재 후보 SQL을 적용하고 runtime 그룹을 상속한 합성 로그인 역할이 약관 조회·동의 삽입을 수행하며 포인터 수정, 동의 삭제, 기존 단일 동의 조회를 하지 못하는 것을 확인했다. `anon`, `authenticated`, `service_role` 직접 접근 및 런타임 무단 변경 거부, 버전 변경에 따른 구버전 차단 관련 테스트도 통과했다. 로컬 시험은 운영 Supabase 관리자 권한, 실제 기본 ACL, 네트워크, 백업, Cloudflare Hyperdrive와 여러 위치의 동시성 검증을 대신하지 않는다. Supabase의 [Data API 보안 안내](https://supabase.com/docs/guides/api/securing-your-api)는 GRANT와 RLS를 함께 점검하도록 설명한다.


## 2026-11-10 Hyperdrive 한정 시험

운영 전용 Hyperdrive에 원격 미리보기에서 최대 두 연결만 열어 무작위 advisory transaction lock의 상호 배제와 COMMIT·ROLLBACK 후 해제를 확인했다. 회원·약관 테이블을 읽거나 변경하지 않았다. 실제 연결 상한 포화, 여러 Worker의 경쟁 및 분리 동의 스키마의 실행은 검증하지 않았다. 별도 격리 DB·Hyperdrive 시험용 `hyperdrive-isolation-probe.mjs`를 추가했고 합성 모의 테스트 2건은 통과했다. 테스트 접두사와 명시적 격리 확인은 대상 격리를 보장하지 않으므로 실행 전 별도 검증이 필요하다. SENS는 보류한다.


## 2026-11-10 격리 Hyperdrive 경합 시험

독립 로컬 TLS Postgres·Tunnel·VPC·Hyperdrive에서 원본 soft limit 5, 캐시 비활성으로 잠금 상호 배제와 커밋·롤백 해제, 클라이언트 연결 6개와 1.5초 동시 트랜잭션 8개(모두 성공, 약 3.759초)를 확인했다. 원본 연결 최고 개수는 측정하지 않았다. 자체 서명 시험 인증서에 대한 VPC 검증이 꺼져 운영 TLS 신뢰 검증과 구별한다. 임시 클라우드 연결과 DB·비밀은 정리했고 운영 DB는 변경하지 않았다. 실제 동의 스키마와 마이그레이션의 격리 Hyperdrive 전 과정 및 운영 최종 권한·백업 검토는 남아 있다.


## 2026-11-10 약관 스키마 격리 Hyperdrive 재시험

합성 격리 로컬 PostgreSQL에 후보 스키마 적용은 성공했다. 별도 Tunnel·VPC를 통한 Hyperdrive 생성은 터널 설정 GET에서 warp-routing이 비활성으로 남아 Cloudflare 오류 2015로 실패했다. 이전 성공 설정 순서도 확인했으나 해결되지 않았다. 이번 시험은 Hyperdrive 경유 동의·잠금·버전 전환·롤백의 증거가 아니다. 임시 VPC·터널·DB는 정리했다. 운영 DB 변경과 SENS 발송은 하지 않았다.


## 2026-11-10 격리 Hyperdrive 스키마 검증 성공

별도 로컬 Postgres·Tunnel·VPC·Hyperdrive에서 후보 동의 스키마에 대해 합성 SQL을 실행했다. 이용약관·개인정보 동의 기록, 트랜잭션 롤백, 공유·독점 잠금 경합과 해제, 개인정보 활성 버전 변경 후 이전 버전 동의 거부 및 과거 동의 보존을 확인했다. 프론트·인증 앱 핸들러의 실제 전체 경로는 검증하지 않았다. 자체 서명 TLS의 VPC 인증서 검증을 끈 격리 시험이며 운영 TLS 검증이 아니다. 시험 접두사 활성 Hyperdrive·VPC·터널 및 비밀 포함 임시 DB 디렉터리는 0건으로 확인했다. 운영 DB는 변경하지 않았다.

이전 2015 오류는 원인 미특정이다. 터널 설정의 warp-routing=false 표시 상태에서도 이번 VPC 직접 TCP와 Hyperdrive 연결이 성공했으므로 이를 오류의 확정 원인으로 판단하지 않는다. 직접 연결 이후 성공한 이유는 확인되지 않았다.
