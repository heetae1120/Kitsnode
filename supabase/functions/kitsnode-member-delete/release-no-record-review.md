# 회원 탈퇴 무기록 후보 릴리스·되돌리기 검토

이 문서와 `delete-admin-trigger-no-record-review.sql`, `delete-admin-trigger-no-record-rollback.sql`은 검토용이다. 아직 운영에 적용되지 않았다. 각 SQL은 운영 상태와 정확히 일치하는지, 두 광고 스키마의 객체·소유자·권한 및 Storage 호환성이 맞는지 다시 확인해야 한다. 미등록 검토자 UUID 또는 미등록 Storage UUID의 신규 쓰기를 거부하는 기존 계약 변화가 있으므로 전체 호출자 확인 전 활성화하지 않는다.

## 순서

1. 실제 대상 프로젝트·배포 커밋과 이전 Edge 버전, UI 빌드, 현행 광고·Storage 경로를 확인한다. 회원·광고 등 다른 기능의 변경사항을 섞지 않고 배포 및 원상복구 대상을 고정한다. 최신 백업과 복구 절차를 확인한다.
2. `KITS_MEMBER_DELETE_ENABLED`를 false로 유지하고 운영 탈퇴 요청이 비활성인 것을 확인한다. 이전 배포나 진행 중인 요청이 남아 있으면 먼저 정리한다. UI 버튼도 비활성으로 둔다.
3. 양쪽 광고 스키마와 Storage 대상, 각 함수·트리거 이름 충돌 및 권한을 읽기 전용으로 확인한 뒤 승인된 DB 변경을 적용한다. 적용 전후 실패 시 해당 트랜잭션 결과와 migration 이력을 확인하고 임의 재실행하지 않는다. 프리체크·요청 제한 RPC가 service role에서만 실행되는지, 익명·일반 회원은 실행하지 못하는지 확인한다.
4. 새 Edge를 배포하되 플래그는 false로 유지한다. 서버 설정·Supabase Auth getUser·Auth admin deleteUser·공유 데이터 차단·Storage·광고 쓰기와 실패 처리를 격리 환경에서 검증한다. 준비가 확인되면 명시된 운영 설정으로 Edge를 활성화하고, 실제 운영 데이터 변경 없는 범위에서 상태와 오류를 관찰한다.
5. 호환되는 프론트 빌드를 검증한 후 UI를 활성화한다. UI는 서버 capability를 확인하며 공유 참조가 사전 확인된 경우만 409로 표시하고, 503·응답 유실은 처리 결과가 불명임을 안내한다.

## 실패 시

먼저 탈퇴 Edge를 비활성화하고 새 탈퇴 진입을 차단한다. 배포 중인 모든 인스턴스와 이미 시작된 요청이 끝났음을 확인하고 UI도 비활성화한다. 요청 결과가 불명인 경우 반복 삭제를 자동으로 실행하지 않는다. DB 적용이 완료된 경우에만 객체 정의를 대조하고 `delete-admin-trigger-no-record-rollback.sql`을 트랜잭션으로 적용한다. 실패하면 부분 실행을 가정하지 말고 트랜잭션 결과와 객체 상태를 확인한다.

롤백은 이 후보가 만든 14개 트리거, 두 public RPC, 네 private 함수를 제거하고 삭제 요청 제한 테이블만 지운다. 기존 광고·Storage 테이블과 기존 공통 private 스키마는 보존한다. 이 제한 테이블의 카운터는 없어지며 기존에 성공한 회원 삭제나 연쇄 삭제된 데이터를 되돌리지 않는다. 이후 기존 광고 연결 요청·증빙 등록·승인·철회와 Storage 쓰기, 일반 로그인 동작을 점검한다. 필요하면 이전 Edge/UI 코드를 복원하되 배포만으로 이미 삭제된 데이터가 복구된다고 가정하지 않는다.

`tests/member-delete-rollback-local.test.sh`는 별도 로컬 PostgreSQL에서 저장소 광고 마이그레이션을 적용하고, 후보 적용 후 미등록 검토자 쓰기가 거부되는 동작과 롤백 후 기존 광고 증빙·Storage 쓰기가 복원되는 것을 합성 데이터로 확인한다. 광고 테스트 스키마는 같은 DDL을 이름만 바꾼 fixture이고 실제 운영 스키마 전체와 동등하다는 뜻은 아니다. 실제 Edge·배포 플랫폼과 운영 데이터는 검증하지 않는다.
