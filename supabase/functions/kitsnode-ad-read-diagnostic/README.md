# Read-only operator diagnostic candidate

This candidate is **not deployed**. It uses existing Supabase Auth and the server-side operator allowlist, fixes the sole Naver target account to 2632357 and returns only the visibility status and role. It neither writes advertising data nor proves the relationship between a KITSNODE member and an advertiser. The Naver account resolver requires the existing runtime modules under the sibling `kitsnode-ad-api/src` directory; include those dependencies when packaging rather than overwriting the existing deployed API.

The candidate uses the production shared operator rate limiter. An authenticated operator session, deployment access, a verified removal/disable mechanism, and a runtime validation are required before deploying. Supabase's standard function-level JWT verification should be enabled. Do not expose API keys or tokens in logs. A live response would validate only the Naver access mapping, not campaign or performance retrieval. The test ad account currently has no registered ads.

## Prepared operator flow

1. Build the site with `NEXT_PUBLIC_AD_DIAGNOSTIC_PAGE_ENABLED=true`. The isolated `/store/ads/diagnostic/` page uses the normal member session and sends the bearer token only to the fixed Supabase diagnostic endpoint. The endpoint independently checks the operator allowlist; a hidden page or a client-side flag is not an authorization boundary. The page is unlinked and defaults to retired when the flag is unset. Review actual production build variables before any deployment.
2. `diagnosticFiles()` in `package.mjs` returns the explicit relative files for a **new** `kitsnode-ad-read-diagnostic` function; use entrypoint `index.ts`, `verify_jwt: true`. Do not deploy over `kitsnode-ad-api`. After deployment test unauthorized request rejection and rate-limit behavior before an operator uses the UI. The actual platform gateway has not yet been exercised; its JWT behavior is not established by local tests.
3. After the read-only check, deploy `diagnosticFiles({disabled:true})` under the **same diagnostic name**, entrypoint `disabled.ts`, `verify_jwt: false`: this version serves no protected data and always returns 410. Turning gateway verification off applies only to the dead endpoint and is necessary to observe 410 without a token. Verify the public endpoint responds 410, then rebuild the site with the page flag unset. Replacing the function is not deletion, and live deployment/disablement has not been tested here.
4. The response does not verify a KITSNODE member's ownership, establish a connection, query campaigns, or prove any advertising performance result. Those require the existing separately authenticated member application and operator review flow.

Checks run locally: handler policy, rate limiter, Deno runtime startup with fake secrets and no external network, unconditional 410 runtime, self-contained deployment bundle `deno check`, isolated browser session UI, typecheck, and builds with the diagnostic page flag on and off. No real credentials or account data were used.
