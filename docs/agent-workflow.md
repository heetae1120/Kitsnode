# 프로젝트 에이전트 협업

## 설정 및 사용

이 저장소의 `.codex/agents/*.toml`은 프로젝트 범위 재사용 역할 정의다. 각 파일은 `name`, `description`, `developer_instructions`를 포함한다. 현재 공식 문서의 독립 TOML 형식을 사용하며 전역 설정, 모델, 권한, MCP 연결을 바꾸지 않는다.

근거: [OpenAI 공식 Subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents) (2026-11-07 확인). 프로젝트 루트에서 시작한 지원 Codex 세션이 역할을 읽는다. 파일 작성은 실행 중인 세션에 역할이 즉시 로드되었거나 에이전트가 항상 실행 중이라는 뜻이 아니다. 클라이언트의 역할 발견을 확인하고 필요하면 새 프로젝트 세션을 연다. 구버전에서 지원되지 않으면 역할 지침을 명시적으로 전달해 위임하고 제한을 보고한다.

## 역할별 인계

1. PM: 사용자 요청을 두 저장소의 범위/비범위, 인수 기준, 위험, 담당 파일로 나누고 작업 순서를 정한다. 각 역할에 필요한 정보와 승인 범위를 전달한다.
2. 기획자: 실제 화면·계약을 읽고 사용자 흐름, 상태/오류, 수용 조건, 양쪽 영향, 미결정을 정리한다. 승인 없이 범위를 늘리지 않는다.
3. 디자이너: 기획을 받아 화면 계층, 토큰, 컴포넌트 상태, 접근성, responsive 기준과 시각 QA 항목을 전달한다. 구현 파일을 개발자와 동시에 편집하지 않는다.
4. 개발자: 합의한 파일 범위만 구현하고 계약·계산 로직을 보존한다. 변경 파일, 실행 명령/결과, 양쪽 회귀 위험을 반환한다.
5. 기획자와 디자이너가 인수/시각 기준으로 검토하고 PM이 결과와 남은 위험을 사용자에게 보고한다. 검토 완료는 운영 배포 승인과 별개다.

기획·디자인 역할은 기본적으로 읽기/제안 중심이고 개발 역할이 코드 작성 책임을 갖는다. 역할 지침은 별도 보안 sandbox가 아니며 실제 권한은 부모 세션에서 상속된다. 병렬 작업 시 같은 파일에는 하나의 작성자만 둔다. 변경할 파일과 협업 중인 변경을 먼저 확인하고 타인의 변경을 되돌리지 않는다.

## 첫 작업: 어드민 디자인 시스템

어드민의 폰트/글자 크기·굵기·행간, 버튼/입력 높이, 간격, border-radius, 색상, 그림자, disabled/loading/focus/error 상태를 정의하고 재사용 가능한 디자인 시스템만 구축한다. 이번 작업에서 기존 어드민 화면에는 적용하지 않는다. 기존 편집 UI 마이그레이션은 사용자의 후속 승인 이후 별도 작업으로 진행한다. 참고 화면의 관찰 가능한 패턴을 해석하되 미확인 화면을 확인한 것처럼 설명하거나 비공개 데이터·브랜드 자산을 복제하지 않는다. 어드민 스타일과 방문자 페이지 복사본을 분리하고, 프론트 역할은 계약/DOM 회귀 검토를 담당한다. 구체적인 토큰 값과 구현 범위는 작업 결과로 별도 확정한다.

## 완료 보고 형식

- 결과와 인수 기준 충족 여부
- 변경 파일 및 두 프로젝트 영향
- 테스트 명령, 성공/실패/미실행 구분
- 호환성 위험, 필요한 후속 작업/결정
- 운영 발행·배포 실행 여부(승인 없으면 실행하지 않음)

## 이 프로젝트의 역할 이름

- `front_planner`
- `front_designer`
- `front_developer`

호출 예: “front_planner에게 요구사항과 인수 기준을, front_designer에게 디자인 명세를 맡긴 뒤 front_developer가 합의된 범위를 구현하게 해 주세요.”
