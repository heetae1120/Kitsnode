# Member onboarding and username-login service: isolated candidate

These files are review-only, not mounted into any runtime and not connected to Supabase, a network listener, production settings or the existing site. They use injected Auth, profile, rate-limit and identity adapters. They do not make the signup feature ready for release.

## Intended service contract

- `checkUsername({clientKey, username})`: normalizes and validates the requested username, then calls a private repository availability check. The result is advisory, never a reservation. Both source- and username-specific distributed rate limits are required.
- `register({clientKey, input})`: validates required profile data, all three confirmations and policy versions; invokes the email Auth signup adapter. Only after a uniformly accepted response with an Auth-supplied user ID does it create a short-lived authenticated-encryption draft containing member ID, email, name, username, phone and policy versions. Password and password confirmation are never retained in the draft. It does not claim the username before email confirmation.
- `inspectDraft({clientKey, token, draft})`: only a verified, active email session whose Auth user ID and email match the draft can view the prefill. Do not place drafts, bearer tokens or passwords in URLs, logs, analytics, or referrers. The browser must clear the stored draft after completion, expiry or explicit cancellation.
- `complete({clientKey, token, draft, confirmation, replacementUsername?})`: requires the original matching Auth ID/email and an explicit fresh terms, privacy and age confirmation. The repository must recheck email, email confirmation, current consent and withdrawal state transactionally while claiming a unique username. If another confirmed user claimed it first, allow the rightful account holder to choose another username without another email signup.
- `completeManual({clientKey, token, input})`: allows an active, confirmed email member to re-enter data and re-confirm all three requirements after opening the email link in another browser or losing/expiring the draft. It requires input email to match the verified session and the repository's current DB email. It does not accept a previous email-bound draft from another Auth identity. Existing consent must still be present in the DB; this function doesn't create consent.
- `signIn({clientKey, username, password})`: resolves the private username→Auth ID/email mapping only server-side. Unknown IDs get a random non-deliverable dummy address so the Auth adapter is still invoked. On a successful Auth response the returned ID, confirmed email, mapping and membership gate are checked, and denied sessions are revoked. Public failure bodies are identical for unknown ID, wrong password, unconfirmed identity and denied membership. Only access and refresh tokens are returned; no resolved email or profile data is returned.

`member-onboarding-http-candidate.mjs` demonstrates JSON POST with a 16 KiB streaming body limit, no-store responses, explicit exact-origin CORS including restricted preflight, untrusted request-field overriding prevention and an injected trusted network client identity. This is a candidate adapter, not an independently mounted public endpoint. It must not trust a user-controlled forwarded IP.

## Required before integration

1. Implement and independently audit durable distributed per-network **and** per-username/email rate limits, including failure and abuse/denial behavior. The current code is injected with an interface and rejects calls when that interface fails; no actual distributed limiter exists. Intentional availability responses allow username enumeration by product design; define and test appropriate restrictions.
2. Implement real Supabase Auth adapters. Verify duplicate email behavior, obfuscated user IDs and returned errors across actual provider/project settings. Unknown and existing email signup must not be distinguishable from responses, timing, draft sizes or rate behavior. Ensure verification cannot create an immediately usable session; revoke unexpected sessions. Verify link callback, PKCE/code-verifier handling and email delivery when signup is initiated from a server and the user opens the link on a different device. Do not assume Supabase browser redirect or provider behavior from mock tests.
3. Enforce incomplete-user denial across all real APIs, RLS policies, storage, sessions and Naver signup paths. The existing direct Supabase Auth endpoint can still create a user without this profile. The candidate SQL/profile is not an authorization gate. Prevent direct bypass of feature-flagged routes and check JWT session revocation where needed.
4. Implement a server-only username repository with row-level security/least privilege, current email resolution, approved profile gate and transactional row-lock semantics. The SQL review candidate takes `expectedEmail` and checks the locked current Auth row against it; direct exposure of its private schema is not approved. Review all existing consent, deletion, user identity, email-change and same-user race paths with a real local Supabase stack. Creating Auth user, consent and profile spans separate transactions; recover safely rather than claim atomicity.
5. Put the AES-256 key in protected server configuration, implement key rotation and consistent multi-instance availability, set an approved expiry, and define temporary data retention. GCM integrity doesn't bind draft ownership by itself; the enclosed subject and email are checked against a validated active session. Before exposing the UX, confirm browser storage, XSS implications and one-device/multi-device recovery behavior. This candidate has no persistence layer or token cleanup job.
6. Validate response timing and side channels in the deployed topology. A dummy password call helps equalize paths but this sample does not guarantee timing indistinguishability and provider rate limits can differ. Ensure session revocation works when membership gating or ID mismatch rejects an otherwise successful password login; mock `revokeSession` is not proof.
7. Replace hard-coded temporary consent versions with the authoritative published versions and actually record the newly confirmed consent where required. Current SQL checks the pre-existing consent row; it does not independently persist the second confirmation. Confirm age requirement and existing users/provider linking policy. Do not publish temporary terms.
8. CORS unit and real local Chrome two-origin tests are not production origin/edge gateway configuration verification. Configure exact trusted origin(s) per environment, verify real browser flows and no redirect/callback logs, and avoid broadening existing operation origins.

## Local verification

- `node --test keyword-api/src/member-onboarding-candidate.test.mjs` — synthetic adapters and HTTP boundary.
- `node --test keyword-api/src/member-onboarding-browser-candidate.test.mjs` — local Chrome with two isolated local origins; uses the desktop bundled Playwright/Chrome paths and no real service.
- `./tests/sql/member-profile-candidate.test.sh` — isolated PostgreSQL with test auth tables, including two-session username collision and expected-email match.

All three are local synthetic tests; none validates deployed Supabase Auth, real mail, real Redis/distributed rate limiting, production API gates, data deletion across systems, or deployed routing.
