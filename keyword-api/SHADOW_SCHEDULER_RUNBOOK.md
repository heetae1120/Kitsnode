# 모의 스케줄러 운영 준비 메모

이 실행기는 명시적으로 활성화하기 전에는 시작하지 않으며, 실제 네이버 입찰가나 광고 상태를 변경하지 않는다. 요일별 1시간 단위 시간표는 한국 시간 기준이다. 운영 적용 전 실제 Supabase·네이버 읽기 연동 및 감독 체계 검증이 필요하다.

## 장애 관측과 시간 초과

실행기는 매 작업의 상태, 허용된 장애 사유 및 숫자 집계만 JSON 로그로 출력한다. 계정 식별자, 자격 증명, 네이버 응답과 예외 원문은 기록하지 않는다. 완료 결과에 실패·불확실 건수가 있거나 `unavailable`이 기록되면 운영자가 원인을 확인해야 한다. 집계 로그는 외부 모니터링이나 알림을 자동으로 구성하지 않는다.

한 번의 작업이 기본 10분 안에 응답하지 않으면 `runner_timeout`을 기록하고 해당 타이머를 중단한다. 시간 초과는 실행 중인 Promise나 네이버·DB 요청을 취소했다는 뜻이 아니다. 이전 작업이 나중에 끝날 수 있으므로 동일 프로세스의 타이머는 다시 시작할 수 없고, 자동 재시도도 하지 않는다. 실패 원인과 클레임·이력 상태를 확인한 뒤 감독자가 프로세스 재시작 여부를 결정해야 한다. 정각 클레임의 유일성은 중복 이력 생성 방지를 위한 추가 안전장치이며, 미완료 작업을 강제로 취소하거나 모든 결과를 복구하지는 않는다.

타이머 중단, 프로세스 종료 또는 호스트 중단 동안 놓친 시간은 자동으로 소급 실행하지 않는다. 외부 감독자 설정, 로그 보존·경보 기준, 적절한 처리량과 시간 초과값은 실제 운영 조건에서 별도 검증해야 한다.

## 처리량과 설정 변경

후보는 ID 순으로 나누어 조회하며 전체 페이지를 확인한 뒤 실행한다. 한 번에 100페이지 또는 10,000건을 넘거나 목록의 순서가 잘못되면 해당 회차 전체를 안전하게 중단하고 `candidate_limit` 또는 `invalid_candidates` 로그를 남긴다. 페이지마다 별도 조회하므로 조회가 진행되는 중 새로 ON된 규칙은 해당 회차에 포함되지 않을 수 있고 다음 회차에 반영된다. 기존 규칙을 OFF로 변경하거나 동의를 철회한 경우에는 실행 및 이력 저장 직전에 다시 검사한다.

## 2026-11-17 연결 준비 상태

네이버 클라우드 Cloud Insight에 `kits-shadow-worker` 지표 스키마와 `kits-shadow-alert` 이메일 수신 그룹이 생성되어 있다. 코드에는 별도 opt-in 방식의 지표 전송기가 연결되어 있으며 내부 오류 알림은 File Plugin으로 구성했다. 상세 연결 및 장애 시험 결과는 아래 기록을 따른다.

## 시험 서버 설치 상태

`kits-commerce-test`에 전용 시스템 계정, `/opt/kits-shadow` 코드와 systemd 서비스 파일을 설치했다. 서버의 기존 Node 22 런타임을 사용하며 관련 서버 측 단위 테스트 9개가 통과했다. 설치 당시에는 모의 스케줄러와 지표 전송을 비활성으로 두었으며, 이후 가동 상태는 아래 시험 기록을 따른다. 실제 자동 입찰은 동작하지 않는다.

Cloud Insight에는 시험 서버만 포함하는 `kits-shadow-test-server` 대상 그룹, 상세 모니터링 및 전용 프로세스 플러그인을 설정했다. `agent_status > 0`을 감지해 `kits-shadow-alert` 그룹에 이메일을 보내는 시험 서버 전용 이벤트 규칙을 만들었으나, 서버 에이전트 장애 유발 시험은 아직 하지 않았다. 이후 프로세스 경보와 수신 시험 결과는 아래 시험 기록을 따른다.

사용자 승인 후 `kits` 프로젝트에 시간표와 클레임 스키마를 적용했다. 기존 수동 규칙 두 건은 유지되고 시간표 및 클레임은 0건이며, 서비스 역할로 후보 조회 RPC가 정상 응답했다. 예약 RPC 6개는 일반 사용자에게 실행 권한이 없고 클레임 테이블의 RLS는 활성화되어 있다. 네이버 쓰기 동작은 활성화하지 않았다.

## 시험 서버 실제 가동과 장애 시험

인증정보 입력 후 읽기 전용 모의 스케줄러와 지표 전송을 켜고 systemd 서비스를 활성화했다. 실제 자동 입찰과 네이버 입찰가 변경은 계속 중단되어 있다. 예약된 규칙이 0건인 상태에서 모의 실행 성공 로그를 확인했으며, 시험 서버에서 유니킴의 검색광고 API 고객 ID로 캠페인 5건을 읽었다. 광고 계정 ID와 API 고객 ID는 다르므로 서로 바꾸어 사용하지 않는다.

Cloud Insight QueryData로 사용자 지표 수집을 확인했고, 프로세스 수집 0 경보를 시험 서버에 한정하여 만들었다. 감독기를 의도적으로 중지했을 때 실제 CRITICAL 이벤트와 수신 그룹 이메일 도착을 확인한 다음 감독기를 다시 시작하고 모의 실행 성공 로그 및 경보 해제를 확인했다. 서버 에이전트 중단 경보의 실제 장애 유발 시험은 하지 않았다.

## 모의 실행 내부 오류 알림 시험

감독기는 정상적이고 지연되지 않은 모의 실행 후에만 `/run/kits-shadow/healthy` 파일을 유지한다. 내부 오류나 결과 지연을 감지하면 파일을 제거하며, Cloud Insight의 시험 서버 전용 File Plugin과 `kits-shadow-test-simulation-unhealthy` 규칙이 파일 부재가 2분간 지속될 때 이메일을 전송한다. 모의 실행의 Supabase 조회에 임시로 잘못된 인증값을 주입해 감독기가 살아 있는 상태에서 `worker_unavailable`과 파일 부재를 확인했다. 실제 장애 이벤트와 이메일을 확인한 뒤 임시 설정을 제거하고 정상 실행과 파일 복구, 이벤트 종료 및 해결 이메일을 확인했다. 시험용 스키마와 리소스는 삭제했다. 실제 입찰 변경은 실행하지 않았다.

## 클레임 검토 개선안의 배포 제한

오래된 클레임 감지 및 운영자 검토 기록은 로컬 초안이며 이 서버나 실제 DB에 적용하지 않았다. 공유 service_role 자격증명을 가진 프로세스는 서버의 운영자 허용 목록을 우회해 임의 운영자 ID로 기록할 수 있으므로 해당 DB 설계만으로 신원을 독립 검증할 수 없다. 별도 최소 권한·독립 인증 또는 안전한 승인 분리 및 해결 정책을 검증할 때까지 배포하지 않으며, 단순 검토 기록으로 경보를 해제하거나 클레임을 삭제·재시도하지 않는다. 상세 검토 및 현재 제한은 [클레임 감시 개선안](SHADOW_CLAIM_MONITOR_DESIGN.md)을 참조한다.
